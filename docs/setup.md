# Local setup and testing

The saved demo runs without Cloudinary API calls. Configure a reviewer-session secret to enable its approval and release routes. Cloudinary credentials are needed only for local uploads and live output preparation.

## Start the application

Use Node.js 24 and pnpm 10:

```bash
pnpm install
pnpm dev
```

Open [http://localhost:3002](http://localhost:3002). Keep an existing `.env.local`; do not overwrite it. For a new environment, copy `.env.example` and fill the variables you need. Restart the server after changes.

| Variable                            | Use                                                                              |
| ----------------------------------- | -------------------------------------------------------------------------------- |
| `NEXT_PUBLIC_CLOUDINARY_CLOUD_NAME` | Public product environment name for your own uploads                             |
| `CLOUDINARY_API_KEY`                | Server-side API authentication                                                   |
| `CLOUDINARY_API_SECRET`             | Server-only credential                                                           |
| `DEMO_SESSION_SECRET`               | Random secret, at least 32 characters, for signed review cookies                 |
| `ENABLE_LIVE_PIPELINE`              | `true` enables uploads and standard output preparation in local development only |
| `ENABLE_PAID_ANALYSIS`              | Keep `false`; paid analysis is unavailable                                       |
| `MAX_UPLOAD_BYTES`                  | Application limit, capped at 4,000,000 bytes                                     |

Generate a new session secret with `openssl rand -hex 32` and paste it into your local file. Never commit secrets or include them in screenshots. Only the cloud name is public.

## Exercise the release gate

The storefront output appears in **Output & release** on first load. Selecting another recipe switches the saved preview without creating a run. **Review this output** starts its review; the initial image is not approved or released.

Select **Load saved demo**, inspect the original and output, and accept all three review checks. **Approve output** records your attestations but does not release the image. **Verify & release** checks the exact output again before making the session-scoped download available.

Try the failure cases too:

- Leave one check unticked: approval remains disabled and the API rejects incomplete approval.
- Select **Reject output**: release stays locked.
- Change the output recipe or request: the interface clears stale approval.
- Select **Start new review**: a new run ID replaces the previous review.
- Refresh and select **Resume previous review**: the current session run is restored.
- Wait beyond the twenty-minute run lifetime: prepare and review again.

The saved storefront, social, and catalog WebP files were generated by Cloudinary and verified on October 14, 2026. Source and derived identity are historical evidence. Local checksum and pixel checks run again; no new Cloudinary processing occurs.

## Test a local upload

Add Cloudinary credentials, set `ENABLE_LIVE_PIPELINE=true`, and restart. Select a JPEG, PNG, or WebP, then **Upload & prepare output**.

The signed upload fixes authenticated delivery, public ID, format restrictions, no overwrite, project folder, tag, and session context. Finalization verifies the stored asset by immutable ID. Output preparation performs two Admin reads, one fixed standard eager transformation, and a bounded delivery check. Preview, release, and download of a live output require further delivery reads.

This consumes ordinary Cloudinary quota. Do not repeatedly prepare new runs or change recipes without accounting for that cost. Reusing an unchanged current run avoids another transformation. AI analysis and generation remain off.

Production cannot enable uploads through this flag. The cookie identifies a demo session, not an authenticated person. Client size checks and post-upload validation cannot alone prevent storage-cost abuse.

## API reference

| Endpoint                               | Purpose                                                             |
| -------------------------------------- | ------------------------------------------------------------------- |
| `GET /api/health`                      | Configuration presence and capabilities, with no credential values  |
| `GET /api/demo?recipe=storefront`      | Saved source reference and preview plan                             |
| `POST /api/pipelines/preview`          | Validate a fixed plan without processing                            |
| `POST /api/pipelines/execute`          | Prepare saved output or an enabled local uploaded output            |
| `GET /api/pipelines/current`           | Restore this session's current run                                  |
| `POST /api/pipelines/review`           | Record approve/reject and three explicit checks                     |
| `POST /api/pipelines/restart`          | Clear approval under a new run ID                                   |
| `POST /api/pipelines/release`          | Recheck evidence and delivery before returning a manifest           |
| `GET /api/pipelines/output?run=<id>`   | Reviewer preview; `download=1` additionally requires a released run |
| `GET /api/pipelines/audit?run=<id>`    | Download current run evidence                                       |
| `GET /api/benchmark`                   | Run deterministic checks; `download=1` downloads JSON               |
| `POST /api/ingestions/sign`            | Constrained local upload authorization                              |
| `POST /api/ingestions/finalize`        | Verify the completed upload                                         |
| `GET /api/ingestions/image?asset=<id>` | Original reviewer access                                            |

Health checks and benchmark:

```bash
curl http://localhost:3002/api/health
curl http://localhost:3002/api/benchmark
```

Plan-only request:

```bash
curl http://localhost:3002/api/pipelines/preview \
  -H 'Content-Type: application/json' \
  --data '{"recipe":"storefront","prompt":"Prepare a storefront image for approval."}'
```

Prepare a saved run using a temporary cookie jar:

```bash
pipeline_cookies=$(mktemp)
curl -c "$pipeline_cookies" -b "$pipeline_cookies" \
  http://localhost:3002/api/pipelines/execute \
  -H 'Origin: http://localhost:3002' \
  -H 'Content-Type: application/json' \
  --data '{"source":"demo","recipe":"storefront","prompt":"Review the saved output."}'
```

Use the returned `run.id` and the same cookie jar for review/release requests. All mutations require the application's exact origin. Bodies are bounded and strict; extra tool, URL, status, or approval fields are rejected. Cookies and upload tickets never belong in URL parameters.

## Verify changes

```bash
pnpm check
pnpm test:e2e
```

If the editor's dev server is running, use `MEDIA_PIPELINE_TEST_BUILD=true pnpm check` for an isolated production build. Browser tests use port 3003 and `.next-test`. Do not run a build and the browser suite against that directory simultaneously.

## Troubleshooting

| Symptom                                | Check                                                               |
| -------------------------------------- | ------------------------------------------------------------------- |
| Missing keys after editing             | Restart the server; health only checks presence, not authentication |
| Saved output preparation returns `503` | Set a random session secret of at least 32 characters               |
| Upload input disabled                  | Uploads require configured local development and the enable flag    |
| Mutation returns `403`                 | Use the UI or include the exact application Origin                  |
| Run returns `401`                      | Keep the same session cookies; a run lasts twenty minutes           |
| Release returns `409`                  | Review all required checks and verify the current artifact          |
| Download returns `403`                 | Release the approved output first                                   |
| Upstream service returns non-JSON      | The UI shows a friendly error, not a JSON-parser message            |

The output proxy bounds responses, verifies decoded dimensions and the checksum, and disables caching. The demo cannot revoke replayed old signed cookies or provide a durable audit log. Those need server-side persistence before production governance use.
